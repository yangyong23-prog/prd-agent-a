# 样例实例：异常事件（RCC）基线 PRD 章节

> 这是上一份《基线 PRD 章节 Schema》的一个填充样例，用异常事件产品线落地，便于共识。
> 每节给出**载重字段**（非全字段）+ 按新范式写的正文。正文中凡需外部输入的地方就地标记，末尾汇总。

## 标记图例

| 标记 | 含义 | 对应 schema |
|------|------|-------------|
| 【需代码·生成】 | 实建层，从代码/库/消息 schema 直接生成，绑 commit 可再生 | `source_authority: 代码`, `regenerable: true` |
| 【需代码·核实】 | 意图层已有内容，需对照代码确认现状与建成状态 | `source_authority: 判定` + 代码核实 |
| 【需PM·确认】 | 描述性表述，基线测试可信下可倾向按代码更新，PM 轻确认 | `nature: 描述性` |
| 【需PM·决策】 | 规范性意图，必须 PM 裁决——代码自证不了"该不该如此" | `nature: 规范性` |
| 【需PM·本体】 | 语义/规范名，对齐本体；PM 或本体 owner 确认 | `ontology_concepts` + 队列类型 `语义冲突/本体缺口` |

## 节 1 · 背景（意图层 · PM 拥有）

```yaml
section_id: SEC-RCC-异常事件-背景-定位
kind: 背景
layer: 意图层
source_authority: 判定
build_status: 已实现
ontology_concepts: [异常事件, 问题, 风险, 风控策略]
review_state: 待PM确认
```

**需求背景**：异常事件是"异常与风险管理"环节的核心概念，集中体现管理标准、各上报渠道的风控策略、以及异常/风险当前是否被及时发现与处理。

**产品目标**：面向客户讲清楚设备设施发生了什么——当前影响、定位的原因、潜在风险、运维响应与处理情况。

**当前存在的问题**（来自历史版本）：专项整改问题关闭后持续时长仍增加（统计不准）；OPS 人工改状态后无法生成异常事件；计划巡检相同三要素同时间观测被抑制（数据丢失）。

> 【需PM·确认】这三条"当前问题"是历史版本写下的动机。基线版多数已做过修复——**需 PM 确认每条在基线下是否仍成立**：仍存在的留作背景，已解决的应移入"版本历史/已解决"，不能当现状写进基线背景。这是纯意图层判断，**不需要代码**。

## 节 2 · 流程（意图层 · 代码可做漂移对照）

```yaml
section_id: SEC-RCC-异常事件-流程-全生命周期
kind: 流程
layer: 意图层
source_authority: 判定
nature: 描述性                # 本节主体描述"现在的流程怎么走"
build_status: 已实现
ontology_concepts: [异常事件, 问题, 工单]
review_state: 待PM确认
```

**阶段序列**（A程序 + 工单系统）：

1. 状态变更记录（入）→ 生成/更新问题
2. 问题 → 判定生成新异常事件 / 合并进已有异常事件
3. 新建/更新异常事件 → 生成排查处理单（或人工解决）
4. 工单流转：指派 → 执行 → 审批（通过→结束 / 不通过→回执行）
5. 工单结束 → 异常事件关闭判断 → 满足则关闭 / 不满足则更新问题回到 2

**输入**：状态变更记录（异常上报、用户报事、IOT 报警、人工修改、数据监控系统、第三方系统报警）。**输出**：问题、异常事件、工单。

> 【需代码·核实】上面的阶段转移与分支需对照实际调用流/状态机核实，重点三处：(a) "人工解决问题 → 直接进关闭判断"这条旁路是否存在；(b) 审批不通过 → 回到执行环节的回环；(c) 关闭判断不满足 → 更新问题 → 回到生成异常事件的回流。用 jQAssistant 调用流 + 实际状态字段比对。
> 【需代码·核实】输入渠道集合要与代码实际支持的渠道对齐（与"节 7 枚举·问题来源"同源，避免两处不一致）。
> 【需PM·决策】"问题的生命周期"里两条是规范性断言，代码即便这么实现也要 PM 确认是否就是意图：① 问题若关联多个异常事件，持续期"取最早结束的那个"；② 问题再次发生时"不影响已结束的异常事件"。

## 节 3 · 规则（意图层 · 含未建成分支，build_status 拆分）

```yaml
section_id: SEC-RCC-异常事件-规则-暂不处理与专项整改
kind: 规则
layer: 意图层
source_authority: 判定
nature: 混合
ontology_concepts: [问题, 异常事件, 工单]
review_state: 待PM确认
```

**场景**：上报状态为 异常/超征兆，且带特殊标记（暂不处理 / 专项整改）。

| 判断点 | 处理 | build_status |
|--------|------|--------------|
| 标记记录 | 问题上记录该标记，问题**不**更新为已解决 | 已实现 |
| 闭合判断 | 该问题视为"已解决"去判断异常事件闭合，并可被统计为故障 | 已实现 |
| 暂不处理标识消失 | 异常事件关闭前、问题被解决后消失；直到关闭仍未解决则不消失 | 已实现 |
| 重复上报抑制 | 暂不处理标识未消失前，A程序不再通知生成新异常事件 | **规划中（原文标"目前未实现"）** |
| 专项整改标识消失 | 不消失 | **规划中（原文标"后续逻辑"）** |
| 对工单影响 | 不影响工单 | **已实现（原文标"暂时"）** |

> 【需代码·核实】上表 build_status 是按原文措辞暂定的——基线版可能已经实现了原文说"未实现"的分支。**逐行对照基线代码确认**哪些真已建成。凡确认仍未建成的，保留为 `规划中`、**不删**，但 RAG 入库时带标签，不能被检索成现状。
> 【需PM·决策】"暂不处理/专项整改视为'已解决'来判断异常事件闭合"是规范性语义，影响统计口径与闭合行为，**需 PM 确认是否为预期**。
> 【需PM·决策】那两条 `规划中` 分支，**是基线该补的功能、还是应从基线 PRD 中剔除**，由 PM 定性。

## 节 4 · 功能（意图层 · 字段计算可对照代码）

```yaml
section_id: SEC-RCC-异常事件-功能-列表字段-事件等级
kind: 功能
layer: 意图层
source_authority: 判定
nature: 混合
ontology_concepts: [异常事件, 问题, 风险分级]
review_state: 待PM确认
```

**字段**：事件等级（列表 + 详情）。

- 生成逻辑：异常事件生成时，按所含问题的风险分级确定，取问题等级最高值（高/中/低/未知）。
- 可改：工单"分类""指派"环节可修改问题等级。
- 人工优先：人工修改事件等级的权重高于计算规则；改后不再随计算结果变化。
- 展示：未解决事件展示"当前等级 + 上次到当前的变化"；已解决事件展示"历史最严重等级"。

> 【需代码·核实】两处计算需对照代码确认字段是否真按此实现：① 是否真"取问题等级最高值"聚合；② 人工修改后是否真有"锁定、不再重算"的覆盖逻辑。这是"字段是否真按文档计算"的可验证部分。
> 【需PM·决策】"人工修改权重高于计算"、"已解决展示最严重 vs 未解决展示当前"这两条是规范性展示意图，代码即便如此实现也**需 PM 确认是否为预期**。

## 节 5 · 接口（实建层 · 整节需代码生成 —— 原文为空）

```yaml
section_id: SEC-RCC-异常事件-接口-工单交互消息
kind: 接口
layer: 实建层
source_authority: 代码
regenerable: true
build_status: 已实现
provenance: { generator: springdoc / 消息schema扫描, generated_from_commit: <基线commit> }
review_state: 草稿            # 原文档此节为空
```

> 【需代码·生成】**整节需从代码生成**。原 PRD 第九章"与工单的交互消息字段说明"只有标题、正文为空，而这是 A程序↔工单系统 最核心的对外契约。生成内容应含：
> - A程序 → 工单系统：消息名 / 触发时机（新问题、合并、关闭通知…）/ 字段 + 类型 / topic 或调用方式
> - 工单系统 → A程序：回传消息 / 触发时机（指派、审批通过、误报核实结果…）/ 字段 + 类型
> 来源：同步看 Feign/RPC 签名，异步看 KafkaTemplate/@KafkaListener + 消息 DTO schema。
> 【需PM·决策（架构）】消息收发方写作"A程序"，需先绑定真实服务名（见文档级悬而未决项）再落。

## 节 6 · 数据（实建层 · 概念模型需换成物理表）

```yaml
section_id: SEC-RCC-异常事件-数据-异常事件对象
kind: 数据
layer: 实建层
source_authority: 代码
regenerable: true
provenance: { generator: pg_dump, generated_from_commit: <基线commit> }
review_state: 草稿
```

> 【需代码·生成】原 PRD 第六章"异常事件对象/问题对象"是**业务概念模型**（属性组+含义），不是物理表。**需用 pg_dump 出的真实表结构替换**：表名 / 字段 / 类型 / 主外键 / 表间关系。

> 【需代码·生成】其中一批属性其实是**计算字段、非存储列**，必须单列标注、不能当库列写：
> - 异常事件"名称" = 实时拼接（对象实例名 + "发现问题：" + 问题名列表）
> - "持续时长" = 当前时间 − 始发时间
> - "最早/最晚要求解决时间" = 跨问题聚合
> - "当前/历史 实际影响、严重程度" = 取决于问题、派生
> 逐个对照代码确认"持久化 vs 运行时计算"。

> 【需PM·本体】真实列拿到后，每列的业务含义需补（代码给不出语义），并把字段命名对齐本体规范名。

## 节 7 · 枚举（混合 · 值需代码、含义需PM/本体，且原文三处不一致）

```yaml
section_id: SEC-RCC-异常事件-枚举-问题来源
kind: 枚举
layer: 混合
source_authority: 代码        # 值
ontology_concepts: [问题来源]
review_state: 待PM确认
queue: [Q-来源枚举一致性]
```

**现状（原文三处不一致）**：
- 数据模型："计划巡检、临时维修、IOT报警、第三方系统报警 等"
- 列表筛选：标"11 种"实际列 10 项，且**不含第三方系统报警**
- 真实判定：又是另一组（含"排查处理、数据监控系统"等）

> 【需代码·生成】**单一来源 = 代码中的来源枚举常量**。以基线代码 enum 为准，列出真实取值，一举解决"10 vs 11""第三方报警是否在内"等冲突，全文各处引用统一指向本节。
> 【需PM·本体】每个取值的规范名对齐本体（如 "数据监控系统 / Ops-IOT / ops_IOT" 归一为一个规范概念）。
> 【需PM·决策】"第三方系统报警在筛选项里缺失"——diff 只能告诉你筛选代码里没有它，**裁不了这是代码漏做（bug）还是文档多写**。需 PM/开发确认：基线筛选是否应支持第三方报警来源。

# 汇总：两张清单

## A. 需代码才能补充/核实（共 across 节）

| 项 | 节 | 类型 |
|----|----|------|
| 基线 commit、运行期 DDL/topic/注册表快照 | 文档级 | 生成 |
| 与工单交互消息契约（整节，原文为空） | 节 5 接口 | 生成 |
| 异常事件/问题对象 → 物理表结构 | 节 6 数据 | 生成 |
| 计算字段 vs 存储列 的逐项判定 | 节 6 数据 | 生成 |
| 问题来源枚举真实取值（解三处冲突） | 节 7 枚举 | 生成 |
| 全生命周期阶段转移/分支/回环 是否如文档所述 | 节 2 流程 | 核实 |
| 输入渠道集合与代码实际支持对齐 | 节 2 流程 | 核实 |
| 规则表各分支真实 build_status（"未实现"是否已建成） | 节 3 规则 | 核实 |
| 事件等级聚合逻辑、人工修改锁定逻辑 是否如文档实现 | 节 4 功能 | 核实 |

## B. 需 PM 再确认/补充

| 项 | 节 | 类型 |
|----|----|------|
| "当前存在的问题"三条在基线下是否仍成立 | 节 1 背景 | 确认 |
| "A程序"绑定到哪个真实服务 | 文档级 / 节5 | 决策（架构） |
| 多异常事件时持续期"取最早结束"、再次发生不影响已结束 | 节 2 流程 | 决策 |
| 暂不处理/专项整改"视为已解决判断闭合"是否预期 | 节 3 规则 | 决策 |
| 两条 `规划中` 分支：基线该补 还是 从 PRD 剔除 | 节 3 规则 | 决策 |
| 事件等级：人工修改优先、解决/未解决展示差异 是否预期 | 节 4 功能 | 决策 |
| 问题来源各值规范名对齐本体 | 节 7 枚举 | 本体 |
| 第三方报警在筛选缺失：代码漏做还是文档多写 | 节 7 枚举 | 决策 |

> 经验观察：**实建层（接口/数据/枚举值）几乎全是"需代码·生成"，意图层（背景/流程/规则/功能）几乎全是"需代码·核实 + 需PM"**——这正好印证了 schema 的两层划分：一层靠代码保鲜，一层靠 PM 拥有终裁，diff 只在中间负责"指出分歧、不替你裁对错"。
