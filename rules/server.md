# apps/server 规则

## 1. 适用范围

本文件适用于 `apps/server` 目录下的服务端代码。

涉及 `apps/server` 改动时，除遵守根目录 `AGENTS.md` 外，还必须遵守本文件。

## 2. 技术栈与职责

- 技术栈：Fastify + TypeScript + Prisma + MySQL
- 主要职责：API 服务、插件、路由、服务端配置、Prisma schema、服务端测试

## 3. 分层要求

- 路由层负责参数接收、鉴权接入、响应组织。
- 业务逻辑应放在 service 或同等职责层，不直接堆在路由处理器中。
- 数据访问应经过可复用、可约束租户条件的访问层或明确封装。
- 当前服务端目录已包含 `routes`、`plugins`、`lib`、`config`、`types` 分层；新增代码应优先延续该结构，不要把插件、配置、路由辅助逻辑混放在同一目录。

## 4. 数据访问与 Prisma

- 涉及业务数据的查询默认应考虑 `tenant_id`。
- 不得绕过租户上下文直接访问业务表。
- 高频查询索引与唯一约束优先包含 `tenant_id`。
- 新增业务表、唯一约束或索引时，应优先评估多租户场景。
- Prisma schema、迁移和生成逻辑仅放在 `apps/server` 体系内维护。
- 数据库结构变更应和服务端实现、契约变更、测试验证保持同步。
- 当前项目已存在 `tenant` 插件为非公开路由注入租户上下文；后续新增受保护路由时，默认应兼容这套上下文，而不是重复从 header 手动取值。

## 5. 配置与环境

- 服务端共享配置优先通过 `@app/config` 读取。
- 环境变量负责注入运行环境、敏感信息和启动时差异，不要把敏感信息写入代码或可提交配置。
- 未确认数据库或环境变量行为前，不要推测迁移结果或启动行为。
- 当前服务端配置由 `loadServerConfig` 聚合 `@app/config` 与环境变量；新增配置项时，应优先在统一配置入口中补齐，而不是在业务代码里直接读取 `process.env`。

## 6. 契约与租户实现

- 路由请求体、响应体、DTO 变更应优先更新 `packages/api-contract`。
- 租户解析、租户注入、租户校验逻辑应保持在后端可信边界内。
- 不允许把前端传入的任意租户值直接当作最终安全依据。
- 当前 `/health`、`/docs`、`/docs/json`、`/auth/login` 已被视为公开路由；新增公开路由时，应显式评估是否需要加入同类白名单，并同步考虑安全边界。
- 当前应用入口 `buildApp` 已集中注册 CORS、JWT、Swagger、tenant plugin 与 routes；新增全局插件时应在该入口统一接入。

## 7. 注释要求

- 对外导出的服务函数、插件注册函数、环境解析入口、复杂查询封装应补充 `JSDoc`。
- 涉及租户约束、鉴权前置条件、事务边界、兼容分支的代码应写清楚意图与限制。
- `tenant` 插件、配置拼装这类带隐式前置条件的逻辑，必须通过 `JSDoc` 写清楚何时生效、依赖哪些环境值、失败时的行为。

## 8. 推荐验证

- 服务端本体验证：

```bash
pnpm --filter @app/server test
pnpm --filter @app/server typecheck
```

- 若涉及数据库结构：

```bash
pnpm --filter @app/server prisma:generate
```

- 若涉及接口行为，应补充或运行 `apps/server` 内对应的 `Fastify.inject()` 测试。

## 9. 禁止事项

- 禁止把核心业务逻辑直接堆在 Fastify 路由处理器中。
- 禁止遗漏 `tenant_id` 条件访问业务数据。
- 禁止只改数据库结构而不同步契约、实现或测试。
- 禁止在多个路由文件里重复维护一套公开路由或租户解析逻辑。
